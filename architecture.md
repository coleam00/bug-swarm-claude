# Architecture

## Stack
- Bun (runtime, package manager, test runner), TypeScript strict, Vite for the browser build, Canvas 2D for the game, Hono on Bun for a small API, SQLite through `bun:sqlite` for runs and scores.
- Why: the bootcamp's supported stack, with the same commands on Windows, macOS and Linux. A game loop needs no UI framework; the server exists for the shared leaderboard and the bet.
- The scaffolded React screen stays only as a thin shell for the start screen and the life-over screen around the canvas. No React in the game loop.
- Release 2 adds Bun's built-in WebSocket server for the arena (no new networking dependency).

## How it runs
- Install: `bun install`
- Develop: `bun run dev` (Vite dev server for the game, with the API server beside it). The stream board is at http://localhost:5173/board and the arena at http://localhost:5173/arena: Vite serves the root `board.html` and `arena.html` there, and proxies the arena's WebSocket (`/ws`) to the API server.
- Start (production mode): `bun run start`: one Bun process serves the API, the built game from `dist/`, `/board`, `/arena` and the arena's WebSocket at `/ws`, on `PORT` (default 3000). `/board` and `/arena` are explicit routes (`src/server/ui.ts`) that serve `dist/board.html` and `dist/arena.html` ahead of the static files and the game's fallback.
- Container: `Dockerfile` builds the game and runs `bun run start` with `NODE_ENV=production`, which makes the server listen on all interfaces; everywhere else it listens on localhost only. `DATA_DIR` must be a persistent volume.
- Health: `GET /health` answers `200 ok` once the app is ready.
- Test everything: `bun run check` (`tsc --noEmit`, then `bun test`). CI runs exactly this.
- The bet's command: `bun run stats`. Moderation: `bun run hide "<name>"`. Balance: `bun run pacing` (release 1). Skill: `bun run skill [--seeds 30] [--max 300]` (release 2: seeded arenas played in-process by the `idle`, `mover` and `aimer` policies; prints each one's median score and life length and exits 1 unless the aimer's median score is at least 2x the mover's; `scripts/skill-lib.test.ts` runs 8 seeds in `bun run check`). Clean slate before the stream: `bun run reset -- --yes` deletes every run and player (hidden names stay); a running server needs no restart.
- Load test: `bun run load -- --url <base url> [--players 500] [--seconds 60]`. Each simulated player (named `load-0000` up, alternating teams) starts a run, plays 5 to 30 s while polling the top 10 and team totals every 4 s, finishes with a score that passes the plausibility check, fetches its best, the top 10 with its rank (`GET /api/top?player=`, which every top 10 read in the test uses) and the team totals as the game-over screen does, and starts again; runs open at the deadline still finish. Beside them, one board watcher per 50 players (at least one) polls `GET /api/board` every 2 s, the board's own cadence. It prints requests, statuses and p50/p95/p99 per route, and exits 1 unless 95% of requests took under 200 ms with no 4xx or 5xx and no network error (a 4xx means the test itself is wrong, such as a 429 from a server started without the raised limit). Every simulated player comes from one IP, so the server under test runs with `RUN_STARTS_PER_WINDOW` raised (it defaults to the real 30; anything but a positive whole number stops the server from starting). Never set it in production. The procedure, with a throwaway data folder (never `data/`):
  - `bun run build`
  - Start the server. bash: `RUN_STARTS_PER_WINDOW=100000 DATA_DIR=<scratch folder> bun run start`. PowerShell: `$env:RUN_STARTS_PER_WINDOW='100000'; $env:DATA_DIR='<scratch folder>'; bun run start`.
  - In a second terminal: `bun run load -- --url http://127.0.0.1:3000`.
  - Then `bun run reset -- --yes` with the same `DATA_DIR`, or delete the folder.
  - The script lives in `scripts/load.ts`; its argument parsing, claims and summary math are in `scripts/load-lib.ts`, which `bun run check` tests. The load run itself is not part of `bun run check`. Every route in its table (`ROUTES`) is called, so none prints an empty row.
- Frame-rate benchmark: `bun run bench`. It builds the game in bench mode and plays a 60 s stress run (150 bugs, every upgrade at its top level) in headless Chrome at 1440x900 and at 390x844 @3x. It prints avg fps, the worst 1 s and `draw()` time, and checks the game-over screen at desktop (1440x900, 1280x720), phone portrait (390x844, 360x640) and phone landscape (844x390, 740x360), 390x844, 844x390 and 740x360 also with a simulated notch, plus the upgrade choice at 740x360 with the notch. The game-over checks inject the worst case: the longest save alert, the longest rank lines, and ten 16-W names at the top score (15,300); at every size each top-10 row must stay one line with its whole score. Headless Chrome reports zero safe-area insets, so the notch is simulated by overriding the `--safe-*` properties in `index.html` that the overlays and the canvas HUD (`hud.ts`) read. `--shots <dir>` saves each layout; `--look <dir>` saves play-screen shots at every size. It needs Chrome (`CHROME_PATH` to point at one), so it is not part of `bun run check`.

## Shape
- Browser game -> HTTP API -> one SQLite file.
- `src/web/App.tsx`: the start screen, the canvas, the game-over screen (with the Tabs vs Spaces race bar). Every page load opens on the start screen: the title over an animated backdrop and either a name field with a button per team (first visit, or "change name") or one "Play as <name>" button for a returning player; `start.ts` (pure, tested) decides which view a player gets and what each button and Enter does, and shows one short message for a refused name. A player's team is stored once, so "change name" shows the other team's button locked. `player.ts` keeps the player in local storage and decides where a later run in the page begins: straight into play once there is a name and a team, else the start screen (a player from before teams picks a team once; a name the rules now refuse is asked for again). The backdrop lives in `src/web/backdrop/`: `sim.ts` (pure, seeded, tested) moves four team robots shooting crawling bugs, `draw.ts` draws it with release 1's sprites and effects, and `index.ts` runs it (paused while the tab is hidden; one still frame with reduced motion; its per-frame cost in `window.bugSwarmBackdrop` in dev and bench builds). Release 2 swaps it for the live arena. `teams.ts` gives each team its label and colour. `hint.ts` (pure apart from local storage, and tested) decides the first-run steering hint over the arena: "Drag anywhere to move" on a coarse pointer, "WASD, arrows or mouse" otherwise, gone on the first steering input (`firstSteer`, which `loop.ts` checks on input events to call `onMove`) or after 4 s. Local storage remembers it was shown (in memory for the page where storage is blocked); a stress run never shows it.
- `src/web/over.ts`: the game-over screen's list of upgrades taken, each with its level, and its rank lines ("Your best is #37 of 214", then "120 points to beat #36" or "You're in the top 10!").
- `src/web/game/`: the game in plain TypeScript.
  - The simulation (robot, bugs, shots, hits, upgrades, spawn ramp) is pure: it advances by a time step from input and state, with no canvas, DOM or clock access, so `bun test` covers it.
  - Upgrades: every 20 s of run time the simulation stops advancing and offers up to 3 different upgrades not yet at their top level (level 2); `choose` takes one and play resumes, so the pause never counts as time survived. The cards are drawn from their own generator, seeded from the run's seed, so a run's choices are deterministic and taking one never changes the swarm.
  - The refactor bomb goes off on its own: once charged, on the first step that starts with a bug in the arena (so never a bug in the step it spawned), it clears every bug (each one counts as a squash) and recharges. The simulation keeps only the run time of its last blast (`bombAt`); its ring and charge indicator are drawn from that (`bombRing`, `bombCharge`).
  - The loop (`loop.ts`) runs on `requestAnimationFrame` with a fixed time step and draws the state to the canvas, scaled to the screen in portrait or landscape. The arena has the same area (360,000 units²) on every screen and the screen's ratio, clamped between 9:16 and 16:9, fixed when the run starts.
  - Drawing: `render.ts` draws a frame from the state and the effects; `sprites.ts` pre-renders the floor, glows, bug and robot sprites on offscreen canvases (rebuilt only when the resolution changes); `look.ts` holds every colour and size, with one entry per bug kind in `BUG_KINDS`.
  - Effects (`fx/`): pure, pooled in typed arrays, tested without a canvas. `changes.ts` finds squashes, hits and test-shield blocks by comparing the bug list between frames (and the hit and block counters), so the simulation needs no event hooks; effects use their own seeded generator, never the simulation's.
  - `config.ts` holds every tuning number (spawn ramp, robot, shots, upgrade strength) and `BUG_KINDS`, the one list of bug kinds the simulation imports; `look.ts` gives each kind its look. The upgrade ids are `UPGRADE_IDS` in `src/server/rules.ts`, so the server checks against the same list; `config.ts` gives each its card text.
  - Input: touch is a floating joystick (`stick.ts` maps the drag: where the first finger lands is the centre, speed grows with the drag up to full at 60 CSS px, a 6 px dead zone stands still, a second finger is ignored, and a faint ring and knob are drawn under the finger); it reaches the simulation as a `"stick"` input whose length is the fraction of full speed. WASD and arrow keys give full speed in a direction, and the mouse (or a pressed pen) steers toward the cursor. 1-3 or tap to pick an upgrade, F for the frame-rate readout on desktop (fps, bugs on screen, effects alive; `fps.ts` is the meter).
  - Stress mode (`?stress=150`, or a bare `?stress`): `createState`'s `stress` option holds the swarm at that many bugs after every step, with every upgrade at its top level and a robot that can't lose, and ends the run at 60 s. It steers itself in a circle until the player steers, and records each frame for the bench. The flag is read only in the dev server and the bench build (`src/web/stress.ts`); a production build ignores it. A stress run is never submitted in any build: no run start, no score, no best.
  - Accidental-input guards (`guard.ts`, pure and tested on the simulation with injected times): game over ignores restart taps, keys and "Play again" for 800 ms after death (`restartIn`), then reveals "Play again" and the hint; the upgrade choice ignores card taps and 1-3 for 350 ms after it shows (`pickChoice`, reached through `loop.ts` `pick`, the one path for both), while the cards fade in. A card tap is timed from when the finger lands, not from the click when it lifts.
  - The API client starts a run and submits its score without blocking the loop; failures are logged and the game-over screen says the score wasn't saved.
- `board.html` (at the root, Vite's second entry) and `src/web/board/`: the `/board` page for the stream, plain TypeScript with no React and no input. `data.ts` checks the `/api/board` body and maps it to what is shown (formatted scores, race shares, which rows are new, whether a team just took the lead) and the join line from the page's own origin; `poll.ts` reads `/api/board` every 2 s, one request at a time, backing off to 10 s while it fails and keeping the last board on screen with a "reconnecting" note; `view.ts` builds the DOM once and updates it in place with `textContent` only, and shrinks a name too wide for its row to fit, down to 5vh (36 px at 1280x720; `NAME_MIN_SCALE` in `data.ts`), cutting it with an ellipsis only below that; `main.ts` wires them. All but `view.ts` and `main.ts` are pure and tested.
- `src/server/app.ts`: `/health`, the icons and the link preview (`/favicon.svg`, `/favicon.ico`, `/apple-touch-icon.png`, `/og.png`, each drawn once on first request and cached for a day), and routes under `/api`: start a run (returns a run id), finish a run (score, squashes, upgrades, device type), top 10 (with `?player=<id>`, also that player's rank: `me`), a player's best, team totals, and the board (top 10 and team totals in one read).
- `src/server/db.ts`: the SQLite file, its tables, `EVENT_TYPES` (`run_started`, `run_ended`) and `TEAMS` (`tabs`, `spaces`; defined in `rules.ts` so the browser can import it, and re-exported here). Schema changes are additive.
- `src/server/rules.ts`: name rules, score plausibility (claimed seconds at most the server's elapsed time plus 2 s slack and at most 300; squashes at most 5 per claimed second; score at most 10 per squash plus 1 per elapsed second; the caps are measured by `bun run pacing --broad`), `UPGRADE_IDS` and `TEAMS`, all pure and tested.
- `src/server/blocked-words.ts`: the name lists: words blocked anywhere inside a word of a name, words blocked only as a whole word, the real words excepted from the first, and the reserved names. `rules.ts` matches them; the file's header says how.
- `src/server/art.ts`: the icons and the 1200x630 link preview, drawn in code from `look.ts` (the robot as an SVG, and a small software rasterizer for the PNGs); `src/server/png.ts` encodes PNG and ICO with `node:zlib`. No image files.
- `src/server/share.ts`: link previews need an absolute image URL, and the app knows no public URL of its own, so the served page takes its origin from the request (`X-Forwarded-Host` or `Host`, and `X-Forwarded-Proto`); a host that is not a plain host name leaves the URL relative.
- `src/server/main.ts`: production entry; reads `PORT`, `DATA_DIR` (default `data/`), the build id (below, "Redeploys") and, for load testing only, `RUN_STARTS_PER_WINDOW` (`src/server/limits.ts`), opens the database and calls `startServer` (`src/server/serve.ts`). That builds the API, adds `GET /api/arena/stats`, then calls `servePages` (`src/server/ui.ts`, tested in `ui.test.ts`), which serves `/board` from `dist/board.html` and `/arena` from `dist/arena.html`, then `dist/` and the page (with absolute share-image URLs, `share.ts`) for every other path; and starts one `Bun.serve` that upgrades `/ws` to the arena's WebSocket and hands every other request to the app (with the server, so the client address still resolves). The arena's integration test (`src/server/arena/ws.test.ts`) starts it on port 0.
- `scripts/stats.ts`, `scripts/hide.ts`, `scripts/reset.ts` (each a one-line wrapper around its command in `scripts/admin-lib.ts`, which returns the exit code and output lines and is tested in-process in `src/server/db.test.ts`), `scripts/pacing.ts`, `scripts/bench.ts`, `scripts/load.ts` (with `scripts/load-lib.ts`, its tested pure half).
- Tests are `*.test.ts` beside the code.

## Arena (release 2)

Release 2 is built beside release 1 and then replaces it. Until the item that switches `/` to the arena merges, release 1's sections above still describe `/`; after it, they describe retired code that the switch item removes.

### Target layout (built up item by item)
- `src/shared/arena/`: the arena simulation, pure and deterministic, used by the server (authoritative) and by the client (prediction of its own robot only). Fixed 50 ms step (20 Hz), a seeded generator, no clock, `Math.random` or DOM. All tuning numbers in one `constants.ts`. World 2400 x 2400 units with walls at the edges.
- `src/shared/arena/protocol.ts`: versioned message types and one validator. Client to server: `hello` (name, team, player id, touch flag), `input` (sequence number, move vector clamped to length 1, aim angle, fire held, dash pressed). Server to client: `welcome` (your entity id, arena id, build id, constants the client needs), `snapshot` (tick, the last input sequence it applied for you, entities in view), `event` (joins, leaves, your life over; later downs, revives, pickups), `error`. Shots, hits and kills travel in snapshots (#55). Malformed, unknown or oversized (over 1 KiB) client messages are dropped; a client sending more than 30 inputs a second is throttled.
- `src/server/arena/`: the room manager (at most 20 players per arena counting bots; join the fullest arena with room for a person, else open a new one; close empty arenas), one 20 Hz tick loop per arena, the `/ws` upgrade on the existing Bun server, server-side fill bots, saving finished lives, and `GET /api/arena/stats` (arenas, people and bots per arena, tick p50/p95 over the last minute).
- `src/web/arena/`: the client: connection and reconnect, input (keyboard, mouse, twin-stick touch, dash button), prediction and reconciliation for your robot, ~100 ms interpolation for everything else, camera, minimap, HUD, and the renderer. The renderer reuses release 1's sprites and pooled effects in `src/web/game/` (robot, bugs, trails, particles, floating text, shake) rather than redrawing them from scratch.
- `scripts/bots.ts` (`bun run bots -- --url <base> --count <n> --seconds <s> [--policy wander|mover|aimer]`): real WebSocket clients for load tests and filling arenas from outside. Prints joins, arenas used, messages per second, errors, and the server's tick p50/p95.
- `scripts/skill.ts` (`bun run skill`): plays seeded arenas in-process with scripted policies and checks the skill gates in `PRD.md`. Its policies (idle, mover, aimer) live in `src/shared/arena/policies.ts`, shared with the server's fill bots and `bun run bots`.

### Built so far (#52, the foundation)
- `src/shared/arena/`: `constants.ts` (every number below), `rng.ts` (mulberry32, copied from release 1 so `src/shared` stands alone), `sim.ts` (players, join and leave, `clampInput`, `stepPlayer`, `stepArena`), `protocol.ts`. Movement: top speed 300 u/s, acceleration 2400 u/s² while a move is held, friction 1800 u/s² while none is: full speed in 3 steps (0.15 s), a stop in 4 (0.2 s, sliding 18 units), a reversal in 0.25 s. Players pass through each other. Fire and dash were carried but did nothing (#55 adds fire; dash still does nothing while alive).
- Protocol: JSON text frames with a `t` field. `welcome` carries the roster (id, name, team); later joins and leaves come as `event`s, so names travel once. Until the Load item, every `snapshot` carries every player in the arena (at most 20) as `[id, x, y, vx, vy, aim]`, positions and velocities to 0.01 and aim to 0.001: about 16 KB/s per player in a full arena, measured then. The players part is encoded once per tick and shared by every socket; only `ack` differed. #55 appends two fields to each row and adds bugs, shots, kills and your own numbers (below): 53 KB/s per player measured with 20 players and about 100 bugs.
- The input contract: the browser sends one input per 50 ms local step and predicts with it; the server queues up to 4 per player (dropping the oldest, and any sequence number not newer than the last), applies one per tick, repeats the last while the queue is empty, zeroes its move after 10 ticks (500 ms) with nothing new, and echoes the last applied sequence number as `ack`. A tick that runs late catches up at most 2 ticks; further lag is dropped.
- `src/server/arena/`: `rooms.ts` (joining, one timer per arena, stats), `room.ts` (the tick), `sockets.ts` (the hello: version, `checkName`, `isBotName` and `isTeam`, else `error` and close 1008; a socket that sends no hello in 5 s is closed; every socket is pinged every 5 s and one silent (no message, no pong) for 15 s is dropped, so a peer that vanished without closing leaves the arena (Bun's idle timeout can't do this: the snapshots keep it alive); inputs limited by `limiter.ts`; frames over 4 KiB close at the transport, 1 to 4 KiB are dropped by the validator), `ticks.ts` (a ring of tick times for the stats), `http.ts`. `isBotName` (`rules.ts`) refuses names starting with `bot ` at `/ws` only; `/` and the boards still accept them until the switch item.
- `src/web/arena/` and `arena.html`: served at `/arena` like `/board`; a player with no name or team is sent to `/`. Prediction (`predict.ts`, replaying unacknowledged inputs through the shared `stepPlayer`, a correction fading over 100 ms), interpolation 100 ms behind (`interp.ts`), the camera (`camera.ts`: release 1's view area, filling the screen, 0.12 s smoothing, the wall plus 60 units in view at the edges), the minimap (`minimap.ts`: 120 px on a phone, 160 px otherwise, top right), controls (`controls.ts`: keys and mouse, or a move stick on the left half and an aim stick on the right), drawing (`render.ts`, release 1's robot, glow, ring and floor grid tile from `sprites.ts`, in team colours) and the connection (`net.ts`: "Reconnecting..." and a rejoin at 0.5 s doubling to 5 s, on a close or after 5 s with no message from the server; a refused name (a `bot ` name, which `/` still accepts) sends the player back to `/`, which keeps the name and says why once (`player.ts` `noteArenaRefusedName`, a note in session storage; `start.ts` `openingNotice`); no build-id reload yet).
- `scripts/bots.ts` (`bun run bots -- --url <base> [--count 18] [--seconds 60]`; `--policy` came with #55), with `scripts/bots-lib.ts`, its tested pure half: bots named `bots-01` up, alternating teams, wandering with a new heading every 1 to 3 s and a slow aim sweep.

### Built so far (#55, aim and fire)
- `src/shared/arena/`: `sim.ts` keeps the state and the step's order; `combat.ts` (shots, heat, the streak, `shotTravelAt`), `bugs.ts` (crawlers, personal spawn pressure, out-of-view spawning), `policies.ts` (`idle`, `mover`, `aimer`, and `observe`). One step: players move (an out player with dash held, 0.8 s or more after going out, respawns at a random spot at least 400 from every bug when 8 tries find one, untouchable for 1 s); alive players fire; bugs spawn, chase and touch; shots fly; the tick counts. Everything in index order from the arena's one generator, so a seed and inputs replay exactly.
- **Shots:** 7 a second while fire is held, from the barrel (the robot's radius plus 6) along the aim plus up to 0.03 rad of spread, at 900 u/s, for 700 units. A shot is swept along its 45-unit step and hits the first bug it touches (a bug already over the barrel is hit at once); one that reaches its range or a wall is a miss. Shots never touch players. Only the life that fired a shot is credited: a shot still flying when its owner's life ends scores nothing.
- **Heat:** each shot adds 1/18; heat cools 0.75 a second once fire is released and the shot cooldown has run out (so tapping does not dodge it); full heat locks the gun for 1.5 s while heat drains to 0. A held trigger locks on its 18th shot, about 2.4 s; bursts kept under the lock sustain about 4.6 shots a second and never lock. The HUD arc flashes from 0.85 heat and while locked.
- **Crawlers:** radius 12, 160 u/s straight at the nearest alive player (ties: the earlier joined), 1 hit point, 10 points. A crawler touching a player who can be hit costs a hit and is gone (no score); the player is untouchable for 1 s; 3 hits end the life. The streak is untouched by hits.
- **Pressure is personal:** each alive player's budget grows by `min(8, 0.3 + 0.05 * life age in s)` bugs a second (capped at 2 owed); each whole bug spawns 560 to 720 units from that player, outside every alive player's view square (800 units, the widest view the camera shows, plus 40, clamped at the walls as the camera clamps), up to 8 tries, else it waits a tick. At most 150 bugs per arena. The wave (1 + every 30 s of arena time) is shown and changes nothing yet.
- **Score:** a kill scores 10 times the multiplier of the streak including that hit: x1, x1.5 from 5 hits in a row, x2 from 10, x3 from 20. A miss resets the streak.
- **Snapshots (protocol v2):** each player row gains `alive` and `untouchable` (0/1), appended. Every snapshot also carries every bug (`b`: id, kind index in `BUG_KINDS`, x, y to 0.1), the shots fired (`s`: id, owner, barrel x, y, angle) and ended (`e`: id, hit, units flown) and the kills (`k`: bug, by, x, y, points) of that tick, and the wave (`w`); the shared part is encoded once per tick. Your own numbers come in `me` (score, kills, streak, multiplier, heat, locked, hits left, alive). Shots are sent only when fired and when they end; the browser flies them with `shotTravelAt`. Your life ending sends you an `over` event (score, kills, seconds). Until the Load item, every bug is in every snapshot: 53 KB/s per player measured with 20 players and about 100 bugs, over the 40 KB/s budget under "Load", which that item's view culling has to bring down.
- **Saving:** `src/server/arena/lives.ts` queues every finished life and writes it on the next turn of the event loop, never inside the tick, as a `run_started` and a `run_ended` (score, kills as squashes, seconds, touch, the player's stored team) through `db.ts`; a failed write is logged as `arena life <run id>: save failed` and play carries on. `startServer`'s `stop()` writes what is queued. A disconnect ends and saves the life in progress, so each drop counts as a run in `median_runs_per_player`. `bun run bots` lives are saved like anyone's: run it only against a scratch `DATA_DIR`.
- **The browser:** the left mouse button, or the aim stick held past its dead zone, fires. Bugs are drawn 100 ms behind like other players, from the snapshot the drawing time is in (a bug vanishes when it is seen to die); other players' shots on that clock, yours at the server's present, so they leave your barrel. Shot ends spark, kills burst and float their points (release 1's pooled particles and text, now with a points argument), a hit shakes the screen and your robot blinks while untouchable. The HUD: score, multiplier (pulsing when it rises), a short "streak lost" when a streak of 5 or more resets, the wave, three hit pips, and the heat arc around your robot. When the life ends: score, kills and length, then after 800 ms any key, click or tap respawns (sent as a dash press).
- `bun run bots` plays `--policy aimer` by default (`wander`, `mover`), seeing bugs and their velocity from snapshots, and prints lives ended and their median score.

### Lives and scores
- A **life** runs from spawn to out (until the revive item: 3 hits; after it, 10 s down with no revive), or until its player leaves (a disconnect: a reconnect starts a new life), or the server shutting down (the Redeploys item; not built yet). When it ends, the server saves it as a run (player id, team, score, kills, length, touch flag) through the existing `db.ts`, so top 10, best, team totals, `/board` and `stats` keep working. Server fill bots' lives, when they come, are never saved; `bun run bots` clients are ordinary players to the server, so theirs are.
- Release 1's run API and its plausibility caps stay only for release 1 until the switch; arena lives are trusted because the server scored them.

### Bug kinds (the recipe)
The first item that adds a second kind builds the seam; every later kind follows it. A kind is one file in `src/shared/arena/bugs/` exporting its constants (hit points, speed, radius, score), its behaviour as a pure step function with explicit phases (for example idle, tell, act, recover), and its spawn rules (which wave unlocks it, its weight in the mix, a cap per arena). One registry lists the kinds; the protocol carries a kind id and phase per bug; the renderer has one draw function per kind in `src/web/arena/draw/bugs/`. Adding a kind touches its own files, the registry, a draw function and tests.

### Pickups (the recipe)
Same shape as bugs: one file per pickup in `src/shared/arena/pickups/` (drop chance by bug kind, how long it lies on the floor, its effect and duration on the player), a registry, a protocol id, a draw function, and a small HUD timer while it is active.

### Redeploys
The server reads its build id from `RAILWAY_GIT_COMMIT_SHA`, else `BUILD_ID`, else the start time. On SIGTERM it ends and saves every life in progress, tells clients `{ type: "error", code: "restarting" }`, then exits. Clients reconnect with backoff (0.5 s doubling to 5 s) and reload the page only when the build id in `welcome` changed.

### Load
Snapshots carry only what is in a player's view plus a margin, quantized positions, and full keyframes every second with deltas between. The budgets: tick p95 under 10 ms with 200 players, and under 40 KB/s per player.

## Data
- **Player:** a random id the browser creates on first visit and keeps in local storage, with a name and a team. No account. The server requires a team for a player id it hasn't seen, stores it once and never switches it; a player from before teams still plays with none.
- **Run:** `run_started` (run id, player id, server time, team) and `run_ended` (run id, score, squashes, seconds, upgrades, touch or not, and the team copied from the start). A run counts for the team its player had when it started; runs with no team (from before teams) count for nobody. A run with no `run_ended` was abandoned.
- **Hidden names:** a table the top 10, the ranks and the board filter on; `bun run hide` adds to it. All of them also leave out, at read time, a stored name that the name lists now refuse (blocked or reserved), so growing a list hides old names without touching stored rows.
- **Top 10 and team totals:** computed from finished, non-hidden runs (`GET /api/top`, `GET /api/teams`), each cached for 1 second so hundreds of clients polling cost one query a second. The top 10 is the first ten rows of one cached ranking of every visible player (`db.ts` `ranking`, read with the hidden names once a second), which also feeds the board and every player's rank. The game-over screen polls both every 4 s. `GET /api/board` returns both from the same two caches, so the board adds no query.
- **A player's rank:** `GET /api/top?player=<id>` adds `me`: `rank` (null when hidden or with no finished run), `ranked` (visible players with a finished run), `next` (the rank above and the points to pass it) and `row` (their index in the returned top 10, or null). Ties go to the player who finished a run first, then the lower player id, as in the top 10, so tied players get distinct ranks and passing a tie takes 1 point. The player's best is read fresh (by index) and ranked against the cached ranking, so a run that just finished ranks at once; `row` follows the cached rows. The game-over screen shows the rank under Best and highlights its own row from `row`, never by matching names.

## Hosting
- Railway, from the `Dockerfile`, with a volume mounted at `DATA_DIR` and GitHub auto-deploy on `main`, so a merged change reaches players within minutes. One instance (SQLite needs one long-running process with a disk). The owner sets up the Railway project; the app only has to honor `PORT` and `DATA_DIR` (and `TRUST_PROXY_HOPS`, below).

### Client IP behind a proxy
The run start limit counts by client IP, and behind Railway the socket address is Railway's proxy, so the client comes from headers (`pickClientIp` in `src/server/app.ts`):
- `TRUST_PROXY_HOPS` unset or `0` (the default, the behaviour before the variable existed): `X-Real-IP`, else the rightmost `X-Forwarded-For` entry, else the socket address. It is not "the socket address only".
- `TRUST_PROXY_HOPS=n`: the n-th `X-Forwarded-For` entry from the right; `X-Real-IP` is ignored. Each trusted proxy appends one entry, so entries a client sends sit further left and can't choose its IP. A missing header, too few entries or an entry that isn't an IP address falls back to the socket address; a bad header never fails the request.
- On Railway the value is `TRUST_PROXY_HOPS=1` (the entry Railway's proxy appends). Use `2` if another proxy, such as a CDN, sits in front of Railway. Railway documents `X-Real-IP` as the client's address but not how it writes `X-Forwarded-For` (docs.railway.com, networking specs and limits), so check it once after deploying. The server logs the client address of the first 20 run starts after boot (`run start 1/20 after boot: client <address>`) and of every refused start, with the cap that refused it. Start a run from a phone on cellular and one from another network, and read Railway's deploy log: the two lines should show two different public addresses. If both show the same address, or a private one (`10.x`, `100.64.x`, `fd..`), the hop count is wrong: unset the variable, which uses `X-Real-IP`, and check again. On stream, `run start refused (per-IP cap)` lines that all show one address mean the same thing.
- Anything but a whole number from 0 to 10 stops the server from starting.

## Boundaries
- No API keys and no outside services. The app starts and `bun run check` passes with no `.env`.
- Public on the internet during the stream: the API accepts only well-formed requests with capped sizes, at most one score per run id, scores that pass the plausibility check, and at most 300 run starts per client IP and 40 per player id per 10 minutes, each refused with 429 and `Retry-After` (sized for many phone viewers behind one carrier IP; `RUN_STARTS_PER_WINDOW` raises both for `bun run load` only; never set in production). A refused start spends neither budget; the game still plays, and game over says "Too many runs right now. Your next run will save."
- Release 1 only: nothing the player does depends on a server response; a run plays with the API down. The arena (release 2) needs its WebSocket by design; when the connection drops it shows "Reconnecting..." and rejoins on its own.
- The `/ws` endpoint is public too: names pass `rules.ts` before joining, the `bot ` name prefix is refused from clients, and inputs are validated and rate-limited.

## Decisions deferred
- Spawn rates, bug speed and upgrade strength: tuned in `src/web/game/config.ts` to the PRD's targets: an idle player loses within 30 to 60 s, and a player who keeps moving survives 1 to 3 minutes, because the gun reloads faster while the robot moves (and the CI drone slower while it stands still). From 60 s the swarm surges: the spawn interval falls again to its last floor and every bug speeds up with run time (`swarmSpeed`), so no upgrade build holds forever. `sim.test.ts` holds both targets with scripted players and upgrade choices off, so they guard the swarm alone. Run length with upgrades is measured by `bun run pacing` (`src/web/game/pacing.ts`): an idle player and a realistic mover (sees bugs within 200 units, reacts 0.25 s late, drifts to the centre, wobbles) through each upgrade order, over seeds 0-49 and both screen shapes; its targets: idle lasts 30 to 60 s on every run, the mover's overall median is 75-120 s, every order's median 55-150 s, and no run passes 240 s; `pacing.test.ts` asserts them on 8 seeds. It also prints the most squashes per run second and the longest run; `bun run pacing --broad` plays seeds 0-124 (2,000 mover runs), and the server's plausibility caps in `rules.ts` are measured from it. How it feels to a human is still the Phase 2 playtest.
- Art: drawn in code on the canvas (see `direction.md`, "The look"). Effects live in `src/web/game/fx/` (particles, trails, screen shake, floating text that merges squashes close in place and time, the shield's pop), pooled so they allocate nothing per frame.
