# Architecture

## Stack
- Bun (runtime, package manager, test runner), TypeScript strict, Vite for the browser build, Canvas 2D for the game, Hono on Bun for a small API, SQLite through `bun:sqlite` for runs and scores.
- Why: the bootcamp's supported stack, with the same commands on Windows, macOS and Linux. A game loop needs no UI framework; the server exists for the shared leaderboard and the bet.
- The scaffolded React screen stays only as a thin shell for the start screen and the life-over screen around the canvas. No React in the game loop.
- Release 2 adds Bun's built-in WebSocket server for the arena (no new networking dependency).

## How it runs
- Install: `bun install`
- Develop: `bun run dev` (Vite dev server for the game, with the API server beside it). The game (start screen, then the arena) is at http://localhost:5173/ and the stream board at http://localhost:5173/board: Vite serves the root `index.html` and `board.html`, and proxies the API and the arena's WebSocket (`/ws`) to the API server. Vite's dev server does not redirect `/arena` (that route is the production server's).
- Start (production mode): `bun run start`: one Bun process serves the API, the built game from `dist/` at `/`, `/board` and the arena's WebSocket at `/ws`, on `PORT` (default 3000). `/board` is an explicit route (`src/server/ui.ts`) that serves `dist/board.html` ahead of the static files and the game's fallback; `/arena` (the arena's address before #64) is a 307 to `/`.
- Container: `Dockerfile` builds the game and runs the server (`bun src/server/main.ts`, what `bun run start` runs, but directly, so the platform's SIGTERM reaches it: "Redeploys") with `NODE_ENV=production`, which makes the server listen on all interfaces; everywhere else it listens on localhost only. `DATA_DIR` must be a persistent volume.
- Health: `GET /health` answers `200 ok` once the app is ready.
- Test everything: `bun run check` (`tsc --noEmit`, then `bun test`). CI runs exactly this.
- The bet's command: `bun run stats` (a run is one arena life). Moderation: `bun run hide "<name>"` (off every board within 5 s, and out of every live arena within 5 s: below, "Built so far (#64)"). Skill: `bun run skill [--seeds 30] [--late-seeds 240] [--max 300]` (release 2: seeded arenas played in-process by the `idle`, `mover` and `aimer` policies; prints each one's median score and life length and exits 1 unless all three gates pass (the aimer's median score at least 2x the mover's, late joiners and the idle newcomer below, #58); the late gate reads 240 seeds by default (owner ruling, #72), about a minute in all, and `--late-seeds 60` is a quick mode, about 15 s, for a first look, not for the verdict; plus an info line, not a gate, placing the server's fill bot between 2x the mover and the aimer (#66); `scripts/skill-lib.test.ts` runs 8 seeds in `bun run check`). Clean slate before the stream: `bun run reset -- --yes` deletes every run and player (hidden names stay); a running server needs no restart.
- Load test: `bun run bots -- --url <base> --count <n> --seconds <s>` (below, under "Arena"), against a server started with a scratch `DATA_DIR` (bots' lives save). The HTTP reads the life-over screen and the board poll are cached for 1 s each (the board's playing count and arenas are read live from the rooms, with no query).
- Multi-player playtest (#94, #95): `bun run playtest -- (--url <base> | --serve) [--players 4] [--seconds 90] [--scenario basic|revive|late-join|restart] [--chrome <path>] [--headed]` (below, "Built so far (#94)" and "(#95)"), against a running server with a scratch `DATA_DIR` (its players' lives save): `bun run build`, then `DATA_DIR=<scratch> PORT=<free port> bun run start`. Or `--serve` (after `bun run build`): the playtest starts the production server itself with a scratch `DATA_DIR` and stops it at the end; `restart` needs this. It needs Chrome, so it is not part of `bun run check`; its pure half is (`scripts/playtest-lib.test.ts`).
- Evidence aid (#85): `BUG_SWARM_START_WAVE=<n>` (off by default) makes each new arena open 10 s before wave n, so a hive queen (wave 5) shows 10 s after an arena opens. For screenshots against a scratch `DATA_DIR`, never in play.
- Release 1's `bun run pacing`, `bun run bench` and `bun run load` were removed with release 1 (#64); they live on the `release-1` branch.

## Shape
- Browser game -> WebSocket arena (and a small HTTP API for the boards) -> one SQLite file.
- `src/web/App.tsx`: the thin React shell around the arena. Every page load opens on the start screen: the title over an animated backdrop and either a name field with a button per team (first visit, or "change name") or one "Play as <name>" button for a returning player; `start.ts` (pure, tested) decides which view a player gets and what each button and Enter does, refuses a `bot ` name before joining, and shows one short message for a refused name. A player's team is stored once, so "change name" shows the other team's button locked. `player.ts` keeps the player (id, name, team) in local storage. A start press mounts the arena (`src/web/arena/game.ts` `startArena`) on a full-screen canvas, with the "Connecting..." / "Reconnecting..." pill, the first-life hint and the life-over screen over it; leaving the arena (a refused name) calls its `stop()`. The backdrop lives in `src/web/backdrop/`: `sim.ts` (pure, seeded, tested) moves four team robots shooting crawling bugs, `draw.ts` draws it with release 1's sprites and effects, and `index.ts` runs it (paused while the tab is hidden; one still frame with reduced motion; its per-frame cost in `window.bugSwarmBackdrop` in dev). Since #79 that drawn backdrop is the fallback under the live arena (below, "Built so far (#79, the live start screen)"). `teams.ts` gives each team its label and colour.
- `src/web/hint.ts` and `src/web/over.ts` (pure, tested): the first-life hint's text and its once-per-browser flag, and the life-over screen's rank line (below, "Built so far (#64)").
- `src/web/game/`: what the arena keeps from release 1, all pure but the sprites: `sprites.ts` (the floor, glows, bug and robot sprites on offscreen canvases, rebuilt only when the resolution changes), `look.ts` (every colour and size, one look per bug kind in `config.ts` `BUG_KINDS`), `config.ts` (the robot's size, the bug looks and the view area), `arena.ts` (the view area for a screen: 360,000 units² in the screen's ratio clamped between 9:16 and 16:9), `fx/` (particles, trails, screen shake and floating text, pooled in typed arrays so they allocate nothing per frame), `stick.ts` (a floating touch stick), `keys.ts` (WASD and arrows to a direction, and F for the readout), `hud.ts` (the HUD's safe-area anchors), `fps.ts`, `rng.ts` and `guard.ts` (`restartIn`: "Play again" ignores input for 800 ms after a life ends). Release 1's simulation, loop, renderer, upgrades and stress mode are on the `release-1` branch.
- `board.html` (at the root, Vite's second entry) and `src/web/board/`: the `/board` page for the stream, plain TypeScript with no React and no input. `data.ts` checks the `/api/board` body and maps it to what is shown (formatted scores, race shares, which rows are new, whether a team just took the lead, the people playing now and the arena pills: one per open arena, "Arena 3 · 14 · wave 7", by id, with the last chip '+N more' when not all fit, `arenaPills`) and the join line from the page's own origin; `poll.ts` reads `/api/board` every 2 s, one request at a time, backing off to 10 s while it fails and keeping the last board on screen with a "reconnecting" note; `view.ts` builds the DOM once and updates it in place with `textContent` only, shows as many arena pills as fit the strip's measured width (all of them when they fit, else the rest folded into '+N more'), and shrinks a name too wide for its row to fit, down to 5vh (36 px at 1280x720; `NAME_MIN_SCALE` in `data.ts`), cutting it with an ellipsis only below that; `main.ts` wires them. All but `view.ts` and `main.ts` are pure and tested.
- `src/server/app.ts`: `/health`, the icons and the link preview (`/favicon.svg`, `/favicon.ico`, `/apple-touch-icon.png`, `/og.png`, each drawn once on first request and cached for a day), and read-only routes under `/api`: top 10 (with `?player=<id>`, also that player's rank: `me`), a player's best, team totals, and the board (top 10 and team totals in one read, plus `playing` and `arenas`: the people playing now and each open arena's people and wave, read live from the arenas through the `live` option, `Rooms.live`; fill bots never count). Nothing writes over HTTP: the server saves arena lives itself.
- `src/server/db.ts`: the SQLite file, its tables, `EVENT_TYPES` (`run_started`, `run_ended`) and `TEAMS` (`tabs`, `spaces`; defined in `rules.ts` so the browser can import it, and re-exported here). Schema changes are additive.
- `src/server/rules.ts`: name rules, `isBotName`, `isShownName` and `TEAMS`, all pure and tested.
- `src/server/blocked-words.ts`: the name lists: words blocked anywhere inside a word of a name, words blocked only as a whole word, the real words excepted from the first, and the reserved names. `rules.ts` matches them; the file's header says how.
- `src/server/art.ts`: the icons and the 1200x630 link preview, drawn in code from `look.ts` (the robot as an SVG, and a small software rasterizer for the PNGs); `src/server/png.ts` encodes PNG and ICO with `node:zlib`. No image files.
- `src/server/share.ts`: link previews need an absolute image URL, and the app knows no public URL of its own, so the served page takes its origin from the request (`X-Forwarded-Host` or `Host`, and `X-Forwarded-Proto`); a host that is not a plain host name leaves the URL relative.
- `src/server/main.ts`: production entry; reads `PORT`, `DATA_DIR` (default `data/`) and the build id (below, "Redeploys"), opens the database and calls `startServer` (`src/server/serve.ts`). That builds the arenas (`Rooms`) and then the API, handing it the arenas' live read for the board, adds `GET /api/arena/stats`, then calls `servePages` (`src/server/ui.ts`, tested in `ui.test.ts`), which serves `/board` from `dist/board.html`, redirects `/arena` to `/`, then `dist/` and the page (with absolute share-image URLs, `share.ts`) for every other path; and starts one `Bun.serve` that upgrades `/ws` to the arena's WebSocket and hands every other request to the app. The arena's integration test (`src/server/arena/ws.test.ts`) starts it on port 0.
- `scripts/stats.ts`, `scripts/hide.ts`, `scripts/reset.ts` (each a one-line wrapper around its command in `scripts/admin-lib.ts`, which returns the exit code and output lines and is tested in-process in `src/server/db.test.ts`), `scripts/bots.ts` and `scripts/skill.ts` (below).
- Tests are `*.test.ts` beside the code.

## Arena (release 2)

Release 2 was built beside release 1 at `/arena` and replaced it at `/` in #64 (release 1 stays on the `release-1` branch). The sections below say what each item built, in order; later items can change what an earlier one says, and say so.

### Target layout (built up item by item)
- `src/shared/arena/`: the arena simulation, pure and deterministic, used by the server (authoritative) and by the client (prediction of its own robot only). Fixed 50 ms step (20 Hz), a seeded generator, no clock, `Math.random` or DOM. Arena-wide tuning numbers in one `constants.ts`; each bug kind's own numbers in its file in `bugs/` (see "Bug kinds"). World 2400 x 2400 units with walls at the edges.
- `src/shared/arena/protocol.ts`: versioned message types and one validator. Client to server: `hello` (name, team, player id, touch flag, and on a rejoin the build id of the page's first `welcome`, #69), `input` (sequence number, move vector clamped to length 1, aim angle, fire held, dash pressed), and since #79 `watch` (the start screen's spectator connection, below). Server to client: `welcome` (your entity id, arena id, build id, constants the client needs), `snapshot` (tick, the last input sequence it applied for you, entities in view: since #89 culled to a view square, quantized, and sent as a keyframe every second with deltas between, `view.ts`), `event` (joins, leaves, your life over, downs and revives (#59), pickups taken and shield blocks (#73)), `error`. Shots, hits and kills travel in snapshots (#55). Malformed, unknown or oversized (over 1 KiB) client messages are dropped; a client sending more than 30 inputs a second is throttled.
- `src/server/arena/`: the room manager (at most 20 players per arena counting bots; join the fullest arena with room for a person, else open a new one; close empty arenas), one 20 Hz tick loop per arena, the `/ws` upgrade on the existing Bun server, server-side fill bots, saving finished lives, and `GET /api/arena/stats` (arenas, people and bots per arena, tick p50/p95 over the last minute, and since #89 the server's memory).
- `src/web/arena/`: the client: connection and reconnect, input (keyboard, mouse, twin-stick touch, dash button), prediction and reconciliation for your robot, ~100 ms interpolation for everything else, camera, minimap, HUD, and the renderer. The renderer reuses release 1's sprites and pooled effects in `src/web/game/` (robot, bugs, trails, particles, floating text, shake) rather than redrawing them from scratch.
- `scripts/bots.ts` (`bun run bots -- --url <base> --count <n> --seconds <s> [--policy wander|mover|aimer|dasher] [--watchers <n>]`): real WebSocket clients for load tests and filling arenas from outside. Prints joins, arenas used, messages per second, errors, and the server's tick p50/p95; with `--watchers` (#79), the KB/s each start-screen watcher receives (`--count 0` measures an empty server's demo arena). Since #89 it also prints per-player KB/s and the server's memory, and gates the run on the "Load" budgets, exiting 1 on a miss (`docs/arena-load.md`).
- `scripts/playtest.ts` (`bun run playtest`, #94): several real browser players in one arena at once, through the real start screen and real input, and a pass/fail table of whether their screens agreed.
- `scripts/skill.ts` (`bun run skill`): plays seeded arenas in-process with scripted policies and checks the skill gates in `PRD.md`. Its policies (idle, mover, aimer, dasher) live in `src/shared/arena/policies.ts`, shared with the server's fill bots and `bun run bots`.

### Built so far (#52, the foundation)
- `src/shared/arena/`: `constants.ts` (every number below), `rng.ts` (mulberry32, copied from release 1 so `src/shared` stands alone), `sim.ts` (players, join and leave, `clampInput`, `stepPlayer`, `stepArena`), `protocol.ts`. Movement: top speed 300 u/s, acceleration 2400 u/s² while a move is held, friction 1800 u/s² while none is: full speed in 3 steps (0.15 s), a stop in 4 (0.2 s, sliding 18 units), a reversal in 0.25 s. Players pass through each other. Fire and dash were carried but did nothing (#55 adds fire, #60 the dash).
- Protocol: JSON text frames with a `t` field. `welcome` carries the roster (id, name, team); later joins and leaves come as `event`s, so names travel once. Until the Load item, every `snapshot` carries every player in the arena (at most 20) as `[id, x, y, vx, vy, aim]`, positions and velocities to 0.01 and aim to 0.001: about 16 KB/s per player in a full arena, measured then. The players part is encoded once per tick and shared by every socket; only `ack` differed. #55 appends two fields to each row and adds bugs, shots, kills and your own numbers (below): 53 KB/s per player measured with 20 players and about 100 bugs.
- The input contract: the browser sends one input per 50 ms local step and predicts with it; the server queues up to 4 per player (dropping the oldest, and any sequence number not newer than the last), applies one per tick, repeats the last while the queue is empty, zeroes its move after 10 ticks (500 ms) with nothing new, and echoes the last applied sequence number as `ack`. A tick that runs late catches up at most 2 ticks; further lag is dropped.
- `src/server/arena/`: `rooms.ts` (joining, one timer per arena, stats, and `live()`: the board's people-only count and arenas, read per HTTP request, never in the tick), `room.ts` (the tick), `sockets.ts` (the hello: version, `checkName`, `isBotName`, a hidden name (#64) and `isTeam`, else `error` and close 1008; a socket that sends no hello in 5 s is closed; every socket is pinged every 5 s and one silent (no message, no pong) for 15 s is dropped, so a peer that vanished without closing leaves the arena (Bun's idle timeout can't do this: the snapshots keep it alive); inputs limited by `limiter.ts`; frames over 4 KiB close at the transport, 1 to 4 KiB are dropped by the validator), `ticks.ts` (a ring of tick times for the stats), `http.ts`. `isBotName` (`rules.ts`) refuses names starting with `bot ` at `/ws`, and since #64 at the start screen too; the boards still show stored ones.
- `src/web/arena/`: the arena client (served at `/arena` by its own `arena.html` until #64, which mounts it at `/` and makes `/arena` a redirect). Prediction (`predict.ts`, replaying unacknowledged inputs through the shared `stepPlayer`, `stepMover` since #60, a correction fading over 100 ms), interpolation 100 ms behind (`interp.ts`), the camera (`camera.ts`: release 1's view area, filling the screen, 0.12 s smoothing, the wall plus 60 units in view at the edges), the minimap (`minimap.ts`: 120 px on a phone, 160 px otherwise, top right), controls (`controls.ts`: keys and mouse, or a move stick on the left half and an aim stick on the right), drawing (`render.ts`, release 1's robot, glow, ring and floor grid tile from `sprites.ts`, in team colours) and the connection (`net.ts`: "Reconnecting..." and a rejoin at 0.5 s doubling to 5 s, on a close or after 5 s with no message from the server; a refused name or team does not retry (since #64 the start screen comes back, below); no build-id reload yet).
- `scripts/bots.ts` (`bun run bots -- --url <base> [--count 18] [--seconds 60]`; `--policy` came with #55), with `scripts/bots-lib.ts`, its tested pure half: bots named `bots-01` up, alternating teams, wandering with a new heading every 1 to 3 s and a slow aim sweep.

### Built so far (#55, aim and fire)
- `src/shared/arena/`: `sim.ts` keeps the state and the step's order; `combat.ts` (shots, heat, the streak, `shotTravelAt`), `bugs.ts` (crawlers, personal spawn pressure, out-of-view spawning; since #65 `bugs/`, one file per kind), `policies.ts` (`idle`, `mover`, `aimer`, and `observe`; #60 adds `dasher`). One step: players move and dash (an out player with dash held, 0.8 s or more after going out, respawns at a safe spot with spawn protection: #58, below); alive players fire; bugs spawn, chase and touch; shots fly; the tick counts (#59 adds the down step before the count and keeps downed players still and silent). Everything in index order from the arena's one generator, so a seed and inputs replay exactly.
- **Shots:** 7 a second while fire is held, from the barrel (the robot's radius plus 6) along the aim plus up to 0.03 rad of spread, at 900 u/s, for 700 units. A shot is swept along its 45-unit step and hits the first bug it touches (a bug already over the barrel is hit at once); one that reaches its range or a wall is a miss. Shots never touch players. Only the life that fired a shot is credited: a shot still flying when its owner's life ends scores nothing.
- **Heat:** each shot adds 1/18; heat cools 0.75 a second once fire is released and the shot cooldown has run out (so tapping does not dodge it); full heat locks the gun for 1.5 s while heat drains to 0. A held trigger locks on its 18th shot, about 2.4 s; bursts kept under the lock sustain about 4.6 shots a second and never lock. The HUD arc flashes from 0.85 heat and while locked.
- **Crawlers:** radius 12, 160 u/s straight at the nearest alive player (ties: the earlier joined; since #59, players who are up, never the downed; a spawn-protected player is chased only by bugs already chasing them, #58), 1 hit point, 10 points. A crawler touching a player who can be hit costs a hit and is gone (no score); the player is untouchable for 1 s; 3 hits ended the life (since #59 they put you down). The streak is untouched by hits.
- **Pressure is personal:** each alive player's budget (since #59, each player who is up: a downed player's waits) grows by `min(8, 0.3 + 0.05 * pressure age in s)` bugs a second (the life's age; on a session's first life 10 s less, #58) (capped at 2 owed); each whole bug spawns 560 to 720 units from that player, outside every alive player's view square (800 units, the widest view the camera shows, plus 40, clamped at the walls as the camera clamps), up to 8 tries, else it waits a tick. At most 150 bugs per arena. The wave (1 + every 30 s of arena time) is shown and changed nothing then (#65: it unlocks bug kinds).
- **Score:** a kill scores 10 times the multiplier of the streak including that hit: x1, x1.5 from 5 hits in a row, x2 from 10, x3 from 20. A miss resets the streak.
- **Snapshots (protocol v2; v3 appends `spawnProtected`, #58 below):** each player row gains `alive` and `untouchable` (0/1), appended. Every snapshot also carries every bug (`b`: id, kind index in `BUG_KINDS`, x, y to 0.1), the shots fired (`s`: id, owner, barrel x, y, angle) and ended (`e`: id, hit, units flown) and the kills (`k`: bug, by, x, y, points) of that tick, and the wave (`w`); the shared part is encoded once per tick. Your own numbers come in `me` (score, kills, streak, multiplier, heat, locked, hits left, alive). Shots are sent only when fired and when they end; the browser flies them with `shotTravelAt`. Your life ending sends you an `over` event (score, kills, seconds). Until the Load item, every bug is in every snapshot: 53 KB/s per player measured with 20 players and about 100 bugs, over the 40 KB/s budget under "Load", which that item's view culling has to bring down.
- **Saving:** `src/server/arena/lives.ts` queues every finished life and writes it on the next turn of the event loop, never inside the tick, as a `run_started` and a `run_ended` (score, kills as squashes, seconds, touch, the player's stored team) through `db.ts`; a failed write is logged as `arena life <run id>: save failed` and play carries on. `startServer`'s `stop()` writes what is queued. A disconnect ends and saves the life in progress, so each drop counts as a run in `median_runs_per_player`. `bun run bots` lives are saved like anyone's: run it only against a scratch `DATA_DIR`.
- **The browser:** the left mouse button, or the aim stick held past its dead zone, fires. Bugs are drawn 100 ms behind like other players, from the snapshot the drawing time is in (a bug vanishes when it is seen to die); other players' shots on that clock, yours at the server's present, so they leave your barrel. Shot ends spark, kills burst and float their points (release 1's pooled particles and text, now with a points argument), a hit shakes the screen and your robot blinks while untouchable. The HUD: score, multiplier (pulsing when it rises), a short "streak lost" when a streak of 5 or more resets, the wave, three hit pips, and the heat arc around your robot (#64 puts the HUD on one line, below). When the life ends the respawn is sent as a dash press (#60 keeps the respawn and the dash apart); #64 replaced the canvas's life-over text and its any-key respawn with the life-over screen.
- `bun run bots` plays `--policy aimer` by default (`wander`, `mover`), seeing bugs and their velocity from snapshots, and prints lives ended and their median score.

### Built so far (#60, dash)
- **The rule** (`sim.ts` `stepMover`, the one step of a robot in a life, used by the server and by the browser's prediction; `stepPlayer` is its no-dash part): a dash press is edge-triggered (an input with `dash` after one without, so holding it dashes once). With the cooldown run out and no dash going, it sets the velocity to 1466.7 u/s (220 units over 0.15 s: 3 ticks of 73.3) along the move direction, normalised so a half-pushed stick dashes as far, or along the aim when no move is held. While dashing the move input is ignored and the walls stop the part of the velocity pushing into them, so a slanted dash slides along a wall. On the tick after, the speed is cut to 300 before the normal step, so a dash covers 220 and does not slide on. The cooldown is 1.5 s (30 ticks) from the press; a press too early, or during a dash, is dropped, not kept for later. The dash draws no randomness, so a seed and inputs still replay exactly. Numbers in `constants.ts` (`DASH_*`).
- **Untouchable:** `canBeHit` (alive, no hit or spawn protection, not dashing) is what a bug's touch checks; the dash's 3 ticks are their own window (`dashTicks`), not `invulnTicks`, so a dash does not blink and leaves hit protection alone. Bugs still chase a dashing robot.
- **Respawns never dash:** while out, `dash` still respawns, and the edge is tracked while out too, so the press that respawned you is not also a dash. A new life (a join or a respawn) cannot dash for 0.5 s (`DASH_SPAWN_LOCK_S`), because a second press can arrive after the respawn (the server clears `dash` on ticks with no new input, and the browser sends presses until it sees you alive).
- **Protocol v3:** each player row appends `dashing` (0/1); your `me` adds `dk` (dash ticks left) and `dc` (ticks until a press is accepted), which the prediction starts its replay from. A full input queue that drops its oldest input carries that input's dash press onto the next one, so a press the browser already predicted is never lost. Cost: 2 bytes per player row and 14 or 15 bytes of `me` per snapshot, about 1.1 KB/s per player with 20 players at 20 Hz, on top of the 53 KB/s measured for #55.
- **Controls:** Space or Shift (key repeats ignored), the right mouse button, or the round dash button (68 px across, 80 px in from the right safe edge and 200 px up from the bottom one, above where the right thumb holds the aim stick, kept under the minimap and on screen; `controls.ts` `dashButtonAt`). Since #64 the button is there only on a touch screen; a finger on it never starts a stick, so one thumb can hold the move stick while the other taps dash. While alive the input's `dash` is the dash press; while out it is the respawn press.
- **Drawing:** your dash is predicted, so it starts on your screen at once. Every dash leaves an afterimage: 4 ghosts of the robot along the dash, fainter the farther back, fading over 0.25 s (cached sprites with `globalAlpha`, nothing allocated per frame). Other players' dashes show from their row's `dashing` flag. Your robot shows the cooldown as a short arc filling in the heat arc's bottom gap (gone once ready), and the dash button sweeps the same fill around its edge, dim while cooling and bright when ready.
- **Skill:** `dasher` is the aimer plus the dash: with its dash ready and a bug within 30 units of touching it (now or a tick on at its velocity), it dashes along the evasion. `bun run skill` prints it beside the others and a `dasher vs aimer` line; the gate is still the aimer against the mover.

### Built so far (#59, down and revive)
- `src/shared/arena/downs.ts`, stepped after shots and before the tick counts. The third hit puts you **down**, not out: `alive` stays true (you are still in the life), `down` is set, you stop where you are, your aim freezes, and you can't move, fire or dash (the dash edge is still tracked, so a dash held through the revive is not a press); `canAct` (up and not down) gates moving, dashing, firing, being chased, being hit (`canBeHit`) and reviving. Bugs chase only players who are up and pass over downed ones; a downed player's spawn budget waits, but bugs still never spawn in their view. Shots already flying from a downed player still score (the life goes on).
- **Revive:** anyone up, of either team, within 60 units (centre to centre, inclusive) for 2 s (40 steps in a row) revives you with 1 hit left and 1.5 s untouchable, and scores 50 on their own life, so for their team. One player holds each down: the nearest in range who is up (ties: the earlier joined) takes hold from 0; if the holder walks off, goes down or leaves, its progress is lost and the next player in range starts over. So a second player in range scores nothing, a revive counts once per down (a later down can be revived and scored again), and a downed player can't revive. A revive on the bleed-out step wins. The holder's streak is untouched.
- **Bleed-out:** 10 s (200 steps) down with no revive ends the life, saved as before (`over` to that player, then a tap respawns). Leaving while down ends and saves the life too.
- **Protocol v4** (#60 took v3 for the dash): snapshots gain `d`, one row per downed player only (`[id, seconds left, reviver or 0, progress 0 to 1]`): 7 bytes (`,"d":[]`) a snapshot when nobody is down, about 20 per downed player. `me` gains `dn` (down 0/1); while down `al` stays 1 and `hl` is 0. Events gain `down` (id) and `revive` (id, by, points), broadcast to every member in the order down, revive, then the tick's lives over, all before that tick's snapshot, so a late joiner sees who is down from the next snapshot alone.
- **The browser:** while down you send no move, fire or dash and predict nothing; you are drawn where the server has you, and a revive restarts prediction from there. A downed robot slumps and flickers inside a red countdown ring, with a pulsing HELP over its name (yours too). A revive in progress draws a ring around both robots, filling in the reviver's team colour. Downed players out of view within 1200 units of you get a red arrow at the screen's edge (`help.ts`, inset by the safe area); their minimap dots blink at 3 Hz. Your own HUD shows DOWN and the whole seconds left, with "A player next to you revives you", in place of the hit pips. A revive floats the reviver's +50 over the revived robot on every screen. Others' down rows are read from the same snapshot their robot is drawn from (100 ms behind), yours from the newest.

### Built so far (#79, the live start screen)
- **The watch connection (protocol v8):** a socket may send `{ t: "watch", v }` instead of a hello. It gets a `welcome` with `you: 0` (player ids start at 1) and the arena's roster, then every event the arena broadcasts (never anyone's `over`) and one snapshot per tick with `ack` 0 and `me` zeroed. It takes no player slot, is never on any roster, nobody is told it came or went, and its inputs are dropped (`sockets.ts`: a watching socket has no room). Watching clears the 5 s hello timer; a wrong version gets `error version`. A `hello` on a watching socket is checked exactly like a first hello, then stops the watch and joins as a player on the same socket.
- **Where a watcher lands** (`rooms.ts` `watch`): the arena with the most people (ties: the lowest id), else the people-less arena with the most watchers, else a new arena: the demo arena, which runs `DEMO_BOTS` (4) server bots while anyone watches it (`fill.ts` `botTarget`: the fill target with people, the demo size with only watchers, else none). A new demo arena is first run `DEMO_WARM_S` (45 s, 900 ticks) forward in one go (`Room.warmUp`: nothing sent, not in the tick stats), because a fresh arena's bots meet their first bugs only about 40 s in (first-life pacing, spawns out of view) and the start screen should show the fight from its first frame. It takes 13 to 27 ms, and runs only when nobody plays anywhere (a demo opens only then), so it holds up no player; nobody ever joins a demo arena, so it skips no one's gentle opening. An arena closes once it has no people and no watchers (`closeIfEmpty`). Every `WATCH_SWEEP_MS` (5 s; a timer that runs only while anyone watches, never in the tick) `rehome` moves the watchers of people-less arenas to the busiest arena with people, sending each a fresh `welcome`, so a start screen opened on an empty server shows the people once they come; the emptied demo arena closes.
- **Fair drop-in kept:** `pick()` never puts a join in an arena with no people (a demo arena watched for an hour is on a late wave), so a watcher who presses Play from a demo arena joins the fullest people arena with room, else a fresh one. `live()` leaves out people-less arenas, so the board and "N playing now" never count or list a demo arena.
- **The cap:** at most `MAX_WATCHERS` (40) watchers server-wide (`Rooms` `maxWatchers`, `startServer` `arenaWatchers`); one more gets `error full` and close 1008, which ends the watch for good (`net.ts` `watching`: any error but `restarting`) and the drawn backdrop shows. A `full` that reaches a connection already switched to playing (Play pressed before the watch's reply arrived) is not final: the server's close rejoins with the hello. The basis: a watcher costs what a player's socket costs, about 65 KB/s in a full arena (#65), so 40 is about 2.6 MB/s at worst, and the snapshot string is built once per tick and sent to every watcher of the arena (`room.ts`, no per-watcher encoding). Watcher frames are never thinned by skipping ticks: shots, ends and kills are per tick. Bringing that under the 40 KB/s budget is the Load item's culling, as for players. Since #89 watchers see the whole arena, not culled, but quantized and as deltas on one shared stream: about 20 KB/s each in a full arena ("Built so far (#89)").
- **The browser** (`net.ts` `watchArena`, `game.ts` `startWatch`, `drift.ts`, `App.tsx` `StartBackdrop`): the start screen runs the arena renderer on its own canvas with no input listeners (the arena's keydown would eat WASD and Space typed into the name field), no HUD (`Scene.watch` skips the hit flash, HUD line, minimap, sticks, dash button, edge arrows and F readout), a backing store at most 1x, and a camera that every 6 s picks the robot with the most bugs within 400 units (a different one when it can) and eases toward it over 2.5 s, never faster than 220 units/s. It fades in (400 ms) on the first snapshot after a welcome; once in, the drawn backdrop's loop is held (its last frame stays under it), and a drop or a refusal runs it again, so there is never a frame showing neither, and the start screen never waits on the socket. No watch with reduced motion; a hidden tab closes the watch (it holds no slot) and a visible one reopens it. A watch never shows a status or reloads: a drop or a restart rejoins quietly, any other error ends it. Its per-frame cost is in `window.bugSwarmWatch` in dev.
- **Play on the same socket:** Play (a team button, Enter or "Play as") calls `handoff()`, which stops the view and returns the open watch connection; the arena's `startArena` calls its `play()`, which sends the hello on the next turn of the event loop (so React StrictMode's immediate unmount, which closes it, never sends a hello and never saves an empty life; in dev the second effect run then connects afresh) and drops a `you: 0` welcome still in flight. A connection that is not open is closed and the arena connects afresh.

### Built so far (#89, stream-scale load)
- **Protocol v11** (`src/shared/arena/view.ts`, the format in `protocol.ts` `WireSnapshot`): the room quantizes its arena once a tick (`quantizeArena`: bugs to whole units, players to 0.1, aim to 0.01, a pickup's time left as the tick it goes, a down as the tick it went down), then writes each member's own snapshot (`encodeView`) against a `ViewState`, its copy of what that member was last sent.
- **What a player is sent:**
  - Every player, never culled: the minimap, the help arrows and the watchers' drift need them all.
  - Every downed player.
  - The bugs, pickups and kills inside a square `VIEW_MAX / 2 + CULL_MARGIN` (600) from where their camera centres. That centre is `bugs/index.ts` `viewCentre`, the camera's clamp at the wall, so the square holds any screen shape.
  - Your own kills wherever they are.
  - The shots fired within `SHOT_RANGE` of the square. A shot's end goes where its start went, judged by where it started (the room remembers).
  - `CULL_MARGIN` (200) covers `VIEW_PAD`, the largest bug's radius, 100 ms of a dasher's lunge and pop-in. Under latency a dash can put the predicted camera about 220 units ahead of the server's square. A dash lasts 0.15 s, so the next snapshot catches up.
- **Keyframes and deltas:**
  - A keyframe (`key: 1`) is whole. It carries `you` and the minimap's far bugs `m` (every bug outside the square but globs, in 16-unit cells, so the swarm stays on the minimap at 1 Hz).
  - It is sent as the first snapshot after every welcome (a join, a watch, a rehome), every `KEYFRAME_TICKS` (20, one second), and the tick after a send Bun dropped (`sockets.ts`: `send` returning 0; -1, queued under backpressure, counts as delivered).
  - A delta (`base`: the tick of the snapshot before it) carries, in mirror order and without ids: integer position differences of every bug and player, the tail changes (a beetle's turn, a dasher's ticks in its tell), the rows that came and went, and `me`'s changed keys. It also carries the tick's events, as before.
  - Differences are taken from the quantized values last sent, so they never drift.
  - Your own `me` carries your exact `x, y, vx, vy` to 0.01, for reconciliation. Other players' rows have no velocity, since nothing read it.
- **The receiver** (`createSnapshotReader`, one per socket, reset by each welcome) applies each snapshot to its mirror and hands on the same `Snapshot` shape every version had, so `interp.ts`, `game.ts` and the bots' tracker are unchanged.
  - A delta whose base is not the mirror's tick decodes to null, and is skipped until the next keyframe.
  - It derives what the wire leaves out: a pickup's ticks left, a down's seconds left.
- **Watchers** share one `ViewState` with no square: one delta string a tick for all of them. A watcher that is new, rehomed or missed a send gets a keyframe of the same state (`keyframeOf`), encoded once that tick for all such watchers.
- **The browser:**
  - The minimap draws the far cells beside the bugs in view.
  - A walking bug's drawn heading eases toward its direction of travel over about a tick (`interp.ts` `easeHeading`, 0.06 s). Whole-unit positions make one tick's direction a few degrees off: a crawler's p50 2.1 and p95 5.6 degrees, eased to 1.1 and 3.3.
  - The F readout adds the KB/s the socket receives and `ack`, the p95 over 2 s of the time from an input leaving to a snapshot acknowledging it (`netmeter.ts`, fixed rings, nothing allocated per frame).
- **`bun run bots`** decodes as a browser does (a snapshot it cannot decode after a keyframe is a `desync` error). It counts each bot's payload bytes over the run's second half and gates the run on the budgets (`bots-lib.ts` `budgetVerdict`). Its bots now see only their view, so what they observe is no longer `bun run skill`'s perfect information. The skill gates run on the simulation and are unaffected.

  - **roster**: at the end each page's roster (welcome, then joins and leaves) holds every page by id and name.
  - **positions**: every player row two pages had for the same tick is the same (position, aim, alive and the flags), each page's own row left out (it carries its exact `me` numbers). Since #89 players come as deltas against what each socket was sent, so this is what proves the pages' decoders agree.
  - **delivery**: the ticks two pages both received reached them close together, and no tick reached every page more than `INTERP_DELAY_MS` (100 ms) after the one before (the server late: that fails at once). The rule for the cross-page spread (owner, #95): it fails only on a sustained problem, more than 1% of the shared ticks over 150 ms or any one over 250 ms. The count over 100 ms (the screens' interpolation delay) is still reported. Why: an owner run of `revive` failed on 3 ticks whose spread was 101 to 111 ms while every game-state check passed, which is one busy browser, not the game. A gap on one page only is reported, not failed. Measured here: four headless pages on one machine showed a few 100 to 150 ms gaps on one page at a time, mostly on the touch-emulated pages. Each synthetic touch waits on the renderer (p50 24 ms against 9 ms for a mouse event). The same four pages driven by the mouse showed none, nor did two pages. That is the test machine's browser, not the game.
  - **downs** and **revives**: each one any page received reached every page connected then, the same (a revive's reviver and points too) and no more than 250 ms apart across pages (the counts over 100 and 150 ms are reported; a run has a few dozen events, so a 1% share would make one slow event a failure). A run with no down fails, since every life ends through one.
  - **kills**: a kill (by bug id) is the same tick, scorer and points on every page whose view had it.
  - **score**: over each run of ticks in a life, a page's private `me.sc` moves by exactly the points of the kills by its id in any page's kill rows, its revives' points and its queen reward. A shot reaches 700 units, past a view's 600-unit cull square, so a kill can be in no view. A run whose seen kills fall short of its own kill count (`me.ki`) is counted and not judged. Scores come only from those sources: `combat.ts`, `pickups/bomb.ts` (both in kill rows), `downs.ts` (the revive event) and `queen.ts` (the queen event's `paid`).
  - **input**: per page, the input the page sent matches what the harness had dispatched before it (move direction, aim within 0.3 rad while firing, fire), and the server's row for it (paired by `ack`) carries the sent aim and heads along a sent move once it has held 5 ticks (a full turn at `ACCEL`). Each link must hold in 80% of samples. This is the proof that real mouse, keyboard and touch input reached the server.
  - **life over**: each life-over screen shows its over event's score; every life that ranks is on every top 10 read 2 s or more after it ended (the read is cached 1 s); and two pages' reads with no life ending between them show the same top 10.
  - **revive scenario** (revive only): the victim went down and the reviver, not someone else, revived it, and every page had that revive at the same tick.
- **Device scale:** the phones are emulated at device scale 1. At 2, Chrome delivered the first touch of each new touch sequence at half its coordinates (measured here), which put the move thumb's stick in the wrong place.
- **Measured** (the factory's Windows machine, headless Chrome, against `bun run start` on the production build with a fresh scratch `DATA_DIR`, `.evidence/94/`): both scenarios pass with 4 pages (2 desktop, 2 touch) in one arena. `basic` (90 s, then the end phase): 15 downs and 7 revives on every page; 879 kills, 792 of them seen by two or more pages, all agreeing; 5 life spans whose scores matched exactly; input 100% on three pages and 93% (dispatched to sent) on one touch page; cross-page spread p50 0.0 ms, p95 9.0 ms, max 89.1 ms; no tick late from the server; 4 one-page gaps of 100 to 139 ms, all on the touch pages. `revive`: A went down at 20 s and B revived it 3 s later, the same revive at tick 327 on all four pages; spread max 99.9 ms (one page's lag, just under the limit); 1 one-page gap of 151 ms on a touch page. The 15 s screenshots show the same robots, bugs and shots on the desktop and phone pages at the same moment, and the life-over screens show one top 10 with all four names. Then 3 more runs of each on the final code (the positions check added): all 6 passed, with 33,067 to 38,269 player rows compared across pages per run, all the same, and the victim revived by B each time. The cross-page spread max read 84.1 to 97.9 ms, close to the 100 ms limit, from one page's lag. Each run had 2 to 15 one-page gaps of 100 to 150 ms, all on the touch pages. So on a busy machine the spread check sits near its limit; it held in 8 runs of 8.

### Lives and scores
- A **life** runs from spawn to out (3 hits put you down; 10 s down with no revive is out, #59), or until its player leaves (a disconnect: a reconnect starts a new life), or the server shutting down (a redeploy, #69: every life in progress ends there with its score so far and is saved; "Redeploys"). When it ends, the server saves it as a run (player id, team, score, kills, length, touch flag) through the existing `db.ts`, so top 10, best, team totals, `/board` and `stats` keep working. Server fill bots' lives are never saved (#66); `bun run bots` clients are ordinary players to the server, so theirs are.
- Lives are the only runs written since #64 (the run API and its plausibility caps went with release 1); they are trusted because the server scored them. Release 1's saved runs stay readable in the database and rank beside lives until `bun run reset`.

### Bug kinds (the recipe)
Built with the second kind (#65); every later kind follows it.
- **The simulation** (`src/shared/arena/bugs/`): a kind is one file exporting a `BugKindDef` (`kind.ts`): its `phases` (names, in order; phase 0 is the quiet one), `radius`, `hp`, `points`, its `spawn` rules (`unlockWave`, `share(lifeSeconds)`, `maxPerArena`), an optional `shell` (#80, below) and `step(bug, target, targetAge)`, a pure step that moves the bug and its phase and allocates nothing. `targetAge` is the target's pressure age in seconds (`pressureAge`, below; 0 with no target), so a kind can spare young lives as the mix does (#72, owner ruling: a spitter never tells at a life under 60 s). **Young lives:** a kind the mix holds back from young lives (its `share` is 0 below its own from-age) also treats a target under that pressure age as no target: it does not go for, aim at or attack them (the spitter holds its tell under `SPITTER_FROM_S`, #72; the beetle stands under `BEETLE_FROM_S`, #86; both 60 s). Otherwise a late joiner meets an arena's established bugs of that kind from its first second while an early joiner meets none until its life reaches the from-age, and the late gate fails (it read 0.74x for the spitter, #72, and 0.76x for the beetle, #86, without the rule). A new kind does this from the start, and its stepped tests age their players past its from-age (`aged` in `spitter.test.ts` and `beetle.test.ts`). Two kinds were built before this rule and do not follow it: the crawler (it spawns from a life's first second, so it has no from-age) and the dasher (from 30 s, `DASHER_FROM_S`; it was built before steps were handed `targetAge`, #72). Both go for any life they are handed, and the gates pass with them as they are. Since #72 a step may return `STEP_LAUNCH` (the stepper launches one bug of the kind's `launches` kind from its mouth along its `dx, dy`, unless that kind's `maxPerArena` or the arena's 150 are reached; the launched bug is not stepped until the next tick, but can touch in this one) or `STEP_EXPIRE` (it leaves with no touch, kill or score). A launched kind (the spitter's glob) has a `share` of 0, so the mix never spawns it. `registry.ts` lists the kinds by id (`BUG_DEFS`, a `Record` over `BUG_KINDS`, so an id with no definition does not compile). The stepper (`bugs/index.ts`) treats every kind the same: it spawns, hands each bug the nearest player who is up (or null), and checks contact (touching a player who can be hit, at `PLAYER_RADIUS` plus the kind's radius, costs a hit and spends the bug, in every phase). Shots hit at the kind's radius plus `SHOT_RADIUS` and a kill scores the kind's points times the streak multiplier (`combat.ts`).
- **A shell** (#80): a kind with `shell: { cosHalf }` has a front shell centred on its facing, the bug's `dx, dy` (its step keeps them a unit vector; 0, 0 blocks nothing). A shot that comes at it within `acos(cosHalf)` of straight on (`combat.ts` `shellBlocks`, read from the shot's direction, not where it lands) is blocked: the bug loses nothing, the shot ends there (`ShotEnded.blocked`; a review laser shot stops too, its earlier hits in the step standing, and the block is not a laser hit), and the owner's streak neither grows nor resets (#80: aiming at the shell is not punished twice; #90: the multiplier can't be farmed on one). A blocked shot counts as a hit only so that it never resets the streak. `events.shellBlocks` lists each blocked shot's owner, for `bun run skill`. The policies read the same rule (`policies.ts` `shelledFrom`, with slack), so bots flank.
- **A bug** (`sim.ts` `Bug`) is flat, the same for every kind: id, kind, position, velocity, hit points, target, and five fields a kind's step uses as it likes, all 0 at spawn: `phase`, `phaseTicks` (ticks in that phase), `dx, dy` (a locked unit direction) and `travel` (units left in a committed move). A kind that needs more adds a field there, initialised in `bugs/index.ts` `newBug`, the one place a bug is made (spawns, launches and `testkit.ts` `placeBug`).

Otherwise a late joiner meets an arena's established bugs of that kind from its first second while an early joiner meets none until its life reaches the from-age, and the late gate fails (it read 0.74x for the spitter, #72, and 0.76x for the beetle, #86, without the rule). A kind may be `staysOnContact` (#85: a touch strikes every player it touches that tick and the bug stays) or a `boss` (#85: placed by its own code, never spawned, and left out of `MAX_BUG_RADIUS`; an arena holds at most 150 bugs plus a boss). Shots hit at the kind's radius plus `SHOT_RADIUS` and a kill scores the kind's points times the streak multiplier (`combat.ts`).
- **A shell** (#80): a kind with `shell: { cosHalf }` has a front shell centred on its facing, the bug's `dx, dy` (its step keeps them a unit vector; 0, 0 blocks nothing). A shot that comes at it within `acos(cosHalf)` of straight on (`combat.ts` `shellBlocks`, read from the shot's direction, not where it lands) is blocked: the bug loses nothing, the shot ends there (`ShotEnded.blocked`; a review laser shot stops too, its earlier hits in the step standing, and the block is not a laser hit), and the owner's streak still grows (the item: aiming at the shell is not punished twice). `events.shellBlocks` lists each blocked shot's owner, for `bun run skill`. - **A bug** (`sim.ts` `Bug`) is flat, the same for every kind: id, kind, position, velocity, hit points, target, and five fields a kind's step uses as it likes, all 0 at spawn: `phase`, `phaseTicks` (ticks in that phase), `dx, dy` (a locked unit direction) and `travel` (units left in a committed move), and since #85 a goal point (`gx, gy`) that arena-level code may write (the hive queen's group goal). A kind that needs more adds a field there, initialised in `bugs/index.ts` `newBug`, the one place a bug is made (spawns, launches and `testkit.ts` `placeBug`).
- **The mix:** the first id in `BUG_KINDS` is the base kind (the crawler). A spawn's place is found first; then, only if some other kind is eligible (the arena's wave at least its `unlockWave`, its `share` above 0 for the spawning player's life age, and fewer than `maxPerArena` of it alive), one number is drawn, and the eligible kinds take their shares in `BUG_KINDS` order; the rest is the base kind. With none eligible nothing is drawn, so a crawler-only stretch replays exactly as before. Shares depend on the spawning player's pressure age (`pressureAge`, #58: the life's age, held back 10 s on a session's first life), never the arena's, so a late joiner's opening matches an early joiner's.
- **The protocol** (v6): a bug row is `[id, kind, x, y]`, plus `phase, angle, ticksIn` only while its phase is not 0 (`angle` is `atan2(dy, dx)` to 0.01), so a crawler costs no more than before. A kill row ends with the kind's index. A kind that needs to send more than phase, angle and ticks in it bumps `PROTOCOL_VERSION`. v12 (#85): the hive queen's marker or health travel in the snapshot's `q` and her kill in a `queen` event; a boss's extra state goes there, not in its row. A kind whose facing matters all the time (the beetle's shell, #80) leaves phase 0 on its first step and never returns, so every row it sends carries its angle; the browser turns it the short way between snapshots while its phase is unchanged. v8 (#80): a shot end's `hit` is 2 when a shell blocked it (1 on a bug, 0 at its range or a wall).
- **The browser** (`src/web/arena/draw/bugs/`): a kind is one file exporting a `BugDraw` (`kind.ts`): its `look` (release 1's `BugLook`, built into leg-frame sprites on resize by `sprites.ts` `buildBugLookSprites`), an optional `under` (drawn beneath every body, called for every bug of the kind, culling itself, for lines that reach the screen from a bug that is off it, and marks pinned to the screen's edge: the frame carries the screen inside the safe area, `screenLeft` to `screenBottom`) and `draw` (its body, called when it is in view; `body.ts` `drawBody` draws release 1's walking sprite at any scale, opacity and angle). `index.ts` lists them in `BUG_DRAW`, a `Record` over `BUG_KINDS`. A kill bursts in its kind's glow. The pure part of a kind's look (scales, alphas over a phase) is a function with a test.
- **What adding a kind touches** (the dasher's commit is the example): its id appended to `BUG_KINDS` in `constants.ts`; a drop chance for it in every pickup file (`pickups/<id>.ts` `drop` is a `Record` over `BUG_KINDS`, so it does not compile without; see "Pickups (the recipe)"); `src/shared/arena/bugs/<kind>.ts` and its entry in `bugs/registry.ts`; `src/web/arena/draw/bugs/<kind>.ts` and its entry in `draw/bugs/index.ts`; a glow colour appended to `PALETTE` in `src/web/game/look.ts` if it needs a new one; tests: `bugs/<kind>.test.ts` (its phases by stepping, its spawn rules, its kill) and `draw/bugs/<kind>.test.ts` (its look's pure part). `BUG_DEFS` and `BUG_DRAW` are `Record`s over `BUG_KINDS`, so `tsc` refuses an id missing from either; `registry.test.ts` checks each definition carries its own id and positive numbers (a boss's points are 0: its reward is its own), and `draw/bugs/index.test.ts` that each look has a size and a palette glow. `bun run skill` prints each kind's spawns and hits a life with no change.

### Pickups (the recipe)
Built with the first two pickups (#73); every later pickup follows it.
- **The simulation** (`src/shared/arena/pickups/`): a pickup is one file exporting a `PickupDef` (`kind.ts`): its `id`, the floating `label` everyone sees over whoever takes it ("Test shield!"), `drop` (the chance a kill of each bug kind drops it, a `Record` over `BUG_KINDS`), `floorTicks` (how long it lies on the floor) and `durationTicks` (how long its effect lasts; 0 for an instant pickup, #78, whose effect happens at the take: it sets no effects bit and shows no HUD timer), plus the plain functions that are its effect. `registry.ts` lists them by id (`PICKUP_DEFS`, a `Record` over `PICKUP_IDS`, and `PICKUP_LABELS`). The stepper (`pickups/index.ts` `stepPickups`, step 5 of `stepArena`, after shots and before downs) treats every pickup the same: each active effect of a player who is up counts down a tick; floor pickups age and go at 0; every kill of the step (scored or not) draws exactly one number from the arena's own drop generator (`state.dropRng`, never `state.rng`, so spawns and spread replay as with no pickups), and the pickups take their chances for the kill's kind in `PICKUP_IDS` order (`dropFor`), a kind's chances summed being at most 1; the drop lands at the kill, clamped inside the walls, unless 16 already lie on the floor (`MAX_PICKUPS_PER_ARENA`, 6 until #90; it is lost, never queued); then each floor pickup goes to the first player in the list who is up and within `PLAYER_RADIUS + PICKUP_RADIUS` (12): personal, its effect set to its full duration (taking one you have refreshes it, never shortening one already running, #90), `events.pickups` says who took what. A refactor bomb goes off there (#78); its kills then draw their drops the same way (landing after this step's takes) and the bugs it killed leave the arena in the same step (`combat.ts` `sweepDeadBugs`).
- **A player** (`sim.ts` `Player.effect`) holds the ticks left of each pickup's effect by its index in `PICKUP_IDS`, allocated once at the join; a new life, the life ending and going down clear it. A session's first life (`Player.firstLife`) then starts with the shield's set to `FIRST_LIFE_SHIELD_TICKS` (#90); the testkit's `arenaWith` clears it, so a hand-placed player starts with no effect.
- **An effect has one hook point in the sim:** the shield's `shieldBlocks` is called by `strikePlayer`, the one entry for every hit on a player (bug contact today; a later hit source, such as a spitter's spit, must call `strikePlayer`, never `hitPlayer`); the laser's `laserPierce` is called by `combat.ts` `fireShot`, which stamps the shot, and `stepShots` walks the pierce. A pickup whose effect fits neither point adds its own call where it acts (an instant effect at the take, in `stepPickups`: the refactor bomb's `bombGoesOff`, #78; a CI drone's shots in `stepArena`, beside the gun: `stepDrone`, #84), not a general hook layer.
- **The protocol** (v7): a player row ends with `effects`, a bitmask (bit i while `PICKUP_IDS[i]` is active on a player in a life), so everyone sees the effect; your own `me.fx` carries the ticks left of each, for the HUD timers; `f` lists the floor (`[id, pickup index, x, y, ticksLeft]`, at most 16 rows since #90); events `pickup` (who, `pickup` index) and `block` (whose shield). A new pickup needs no protocol bump while there are at most 31 pickups and what it shows fits in its effects bit and `fx`; one whose effect sends more bumps `PROTOCOL_VERSION`. What can be derived needs no field: the CI drone's position is a pure function of the tick and the holder's id, never sent; its bump (v10, #84) was for marking its shots. An instant pickup shows itself from the `pickup` event every client already gets (the refactor bomb's ring, #78), so it needs no bump either.
- **The browser** (`src/web/arena/draw/pickups/`): a pickup is one file exporting a `PickupDraw` (`kind.ts`): its `glow` (a `PALETTE` index), its `glyph` (drawn on the floor in a pulsing halo and a dark disc, and in your HUD timer) and an optional `on` (what it draws on every robot that has it; it is handed the robot's player id and the tick that robot's shots are drawn at, #84). `index.ts` lists them in `PICKUP_DRAW`, a `Record` over `PICKUP_IDS`. A floor pickup blinks at 5 Hz in its last 3 s (`floorAlpha`, `PICKUP_BLINK_S`). A take floats its label over the taker (`fx/text.ts` `spawnWord`, a prebuilt string, never merged with score labels) with a burst in its glow; your active ones show as 18 px icons under the HUD line (`hudline.ts` `hudIconX`), each with a ring draining as it runs out, pushing "streak lost" and the F readout down.
- **What adding a pickup touches** (#73's commits are the example): its id appended to `PICKUP_IDS` in `constants.ts`; `src/shared/arena/pickups/<id>.ts` and its entry in `pickups/registry.ts`; its effect's one call in the sim; `src/web/arena/draw/pickups/<id>.ts` and its entry in `draw/pickups/index.ts`; a glow appended to `PALETTE` if it needs a new one; tests: `pickups/<id>.test.ts` (its effect by stepping: taken, working, lapsing; an instant one: taken and working) and anything its look adds to `draw/pickups/index.test.ts`. Its drop chances: each kind's total chance of a pickup is split evenly over the pickups that exist, so a new pickup re-splits every file's `drop` (four since the CI drone, #84); `registry.test.ts` checks each kind's sum is at most 1 (the numbers themselves are judged by `bun run skill`, not pinned in a test). `PICKUP_DEFS` and `PICKUP_DRAW` are `Record`s over `PICKUP_IDS`, so `tsc` refuses an id missing from either. `bun run skill` prints each pickup's takes a life with no change; a pickup that changes how long lives last is read on the late gate at `--late-seeds 240` (and 480) before it ships (see "Built so far (#73)" above).

### Built so far (#95, playtest late-join and restart)
- **`late-join`** (at least 3 pages): the last page is not opened until an early page's snapshot reads wave 6 (`LATE_JOIN_WAVE`; the wave is the arena's tick, `(6-1) * WAVE_S` = 150 s in, and it does not stall on the queen), then joins through the start screen like the others and plays at least 30 s (`LATE_PLAY_S`). It stops, and fails, if no wave 6 is read within 210 s. The **late-join scenario** check: the late page's first snapshot (a new socket's first is a keyframe) reads wave 6 or later, and at its tick the late page's roster (its welcome, then the joins and leaves it received before that snapshot) equals what each early page had received by the same tick, as id to name. The other players' rows and the downs (by id, with their timers) are the same as each early page's for that tick, each page's own row left out. Roster, downs, kills and score from then on are the common checks, which include the late page. A run takes about 4 minutes.
- **`--serve`**: instead of `--url`, the playtest starts `bun src/server/main.ts` itself, after `bun run build` (it exits 2 without `dist/index.html`). It picks a free port once, uses a scratch `DATA_DIR` (`.evidence/playtest/data-<pid>`, deleted on a pass, kept on a fail) and a fixed `BUILD_ID` (`playtest-<pid>`), and drops `RAILWAY_GIT_COMMIT_SHA` (it would beat `BUILD_ID`), `NODE_ENV` (production listens on every interface) and `BUG_SWARM_START_WAVE` (`serverEnv`). The server's output goes to `.evidence/playtest/server-<pid>-<n>.log`. It is stopped with the IPC message `shutdown` (`SHUTDOWN_MESSAGE`, `serve.ts`), which `main.ts` routes into the same graceful shutdown as SIGTERM. Why IPC: on Windows a signal to a child process is a hard kill (measured with Bun 1.4.5: the child's SIGTERM handler never ran and it exited 143, while the IPC message reached it and it exited 0). If it has not exited 6.5 s after the message (the 4.5 s shutdown budget plus 2 s), that process, by the PID it was started with, is killed; nothing is ever stopped by name.
- **`restart`** (needs `--serve`): 40 s in (`RESTART_AT_S`) the pages hold still, the server is stopped as above, and started again on the same port, `DATA_DIR` and build. The pages rejoin by themselves (the client's own reconnect, "Redeploys"), and must all have a welcome from the new server within 30 s. Then they play on for 40 s (`AFTER_RESTART_S`). The **restart scenario** check: the old server exited 0 on its own within the shutdown budget; every page was told `restarting`; every page has exactly one welcome from the new server, on the same build (so not "Updating..."), and played at least 35 s on it with inputs sent. The detail names both PIDs, the stop time, the server's own shutdown line (its lives saved) and each page's time from `restarting` to its new welcome.
- **Server lifetimes:** ticks, player ids, bug ids, arena ids and input seqs all start again with a new server process, so every record carries `gen`, the server lifetime it came from, and the checks compare within one: same arena per lifetime; delivery, positions, events, kills and score keyed by lifetime and tick (a score run ends at a restart); input acks paired within a lifetime; and two top 10 reads from different lifetimes are not compared under "no life ending between" (a restart ends every life with no over event). The harness moves every page to the next lifetime only after the old process has exited and before the new one starts, so the stamp is exact. A welcome takes the page's lifetime when it arrives, and every other frame takes its connection's, so a late frame from the old server keeps the old one. A top 10 read takes the lifetime when its response arrived. The restart's own gap is reported in the delivery detail, not judged.
- **No spawned process in `bun run check`:** the IPC hook is tested with a fake emitter (`serve.test.ts`), and the real process path (Windows included) is proved by the `restart` run itself, as `bun run check` spawns no processes since #41.
- **Measured** (the factory's Windows machine, headless Chrome, production build, `.evidence/95/`, 4 pages: 2 desktop, 2 touch; every check passed in each run). `late-join` against a hand-started `bun src/server/main.ts` with a scratch `DATA_DIR`: the late page's first snapshot was tick 3077 (153.9 s in, wave 6, the queen still up), with a roster of 5 and 9 player rows the same as on all 3 early pages, then 54 s of play; spread max 84.9 ms, 0 ticks over 100 ms. `late-join --serve`: first snapshot tick 3071, 57 s of play, spread max 81.8 ms. `restart --serve`: the old server exited 0 33 ms after the IPC message ("shutdown (ipc): 4 lives saved"), the new one answered 0.7 s later, every page had its new welcome 1.5 s after `restarting` (the restart gap on the pages: 1.6 s), and the new server's arena starts at wave 1. Then 40 s of play with 25,362 player rows compared, all the same. `revive --serve`: spread max 98.8 ms, 0 ticks over 100 ms. Every `--serve` server stopped with exit 0 through the IPC message; none was killed.

### Redeploys
The server reads its build id from `RAILWAY_GIT_COMMIT_SHA`, else `BUILD_ID`, else the start time, and sends it in every `welcome`. On SIGTERM or SIGINT, or the IPC message `shutdown` from a parent process (`main.ts`, `gracefulShutdown` in `serve.ts`; the playtest's `--serve` uses the message, since on Windows a signal to a child is a hard kill, #95) it ends and saves every life in progress with its score so far (`Rooms.endAll`, written to the database at once), tells every client `{ t: "error", code: "restarting" }` and closes its socket (1012), refuses any socket or hello that arrives after that the same way, stops listening and exits 0; a backstop exits 1 at 4.5 s whatever is still running. The `Dockerfile` runs the server directly as PID 1 so it receives the SIGTERM. A hard kill (no SIGTERM) loses the lives in progress (owner ruling). Clients show "Reconnecting..." and rejoin with backoff (0.5 s doubling to 5 s, forever) with the same name and team. The browser keeps the build id of its first `welcome` and sends it in every rejoin's `hello`; a server of another build refuses that hello with `{ t: "error", code: "build", build }` before it joins an arena, so the update starts (and saves) no life. That refusal, or an `error version` on a rejoin (the new build changed the protocol), shows "Updating..." and reloads the page, and the reloaded page goes straight back into the arena with the stored name and team (a one-shot flag in sessionStorage, `player.ts`) instead of the start screen. A first join carries no build, and a version error on it stays final ("Reload to update"), so a stale page never loops on reloads.

### Load
Snapshots carry only what is in a player's view plus a margin, quantized positions, and full keyframes every second with deltas between (built in #89: "Built so far (#89)"). The budgets: tick p95 under 10 ms with 200 players, and at most 40 KB/s per player. `bun run bots -- --url <base> --count 200 --seconds 120 --policy aimer` against a production server checks both, and exits 1 on a miss. `docs/arena-load.md` has the method, the machine and the numbers: tick p95 about 2 ms, and at most about 27 KB/s per player.

## Data
- **Player:** a random id the browser creates on first visit and keeps in local storage, with a name and a team. No account. The arena's hello carries a team; the server stores a player's team once and never switches it (a life counts for the stored team); a player from before teams gets one with their first life.
- **Run:** one arena life, written by the server as `run_started` (run id, player id, server time, team) and `run_ended` (run id, score, kills as squashes, seconds, upgrades (always none for a life; release 1 stored its upgrades there), touch or not, and the team copied from the start). A run counts for the team its player had when it started; runs with no team (from before teams) count for nobody. A run with no `run_ended` was abandoned.
- **Hidden names:** a table the top 10, the ranks and the board filter on; `bun run hide` adds to it. All of them also leave out, at read time, a stored name that the name lists now refuse (blocked or reserved), so growing a list hides old names without touching stored rows.
- **Top 10 and team totals:** computed from finished, non-hidden runs (`GET /api/top`, `GET /api/teams`), each cached for 1 second so hundreds of clients polling cost one query a second. The top 10 is the first ten rows of one cached ranking of every visible player (`db.ts` `ranking`, read with the hidden names once a second), which also feeds the board and every player's rank. The life-over screen polls both every 4 s. `GET /api/board` returns both from the same two caches, so the board adds no query, plus the people playing now and the open arenas (people and wave), read live and uncached from the rooms on every request: people only, never fill bots.
- **A player's rank:** `GET /api/top?player=<id>` adds `me`: `rank` (null when hidden or with no finished run), `ranked` (visible players with a finished run), `next` (the rank above and the points to pass it) and `row` (their index in the returned top 10, or null). Ties go to the player who finished a run first, then the lower player id, as in the top 10, so tied players get distinct ranks and passing a tie takes 1 point. The player's best is read fresh (by index) and ranked against the cached ranking, so a run that just finished ranks at once; `row` follows the cached rows. The life-over screen shows where the best stands on the top 10 and highlights its own row from `row`, never by matching names.

## Hosting
- Railway, from the `Dockerfile`, with a volume mounted at `DATA_DIR` and GitHub auto-deploy on `main`, so a merged change reaches players within minutes. One instance (SQLite needs one long-running process with a disk). The owner sets up the Railway project; the app only has to honor `PORT` and `DATA_DIR`. The service must also set `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=5` (or the draining time in its settings): Railway's default is 0, a SIGKILL right behind the SIGTERM, which would lose the lives a redeploy saves ("Redeploys"). (`TRUST_PROXY_HOPS`, which release 1's run-start limit read, is ignored since #64; a leftover value on Railway is harmless.)

## Boundaries
- No API keys and no outside services. The app starts and `bun run check` passes with no `.env`.
- Public on the internet during the stream: the HTTP API only reads, with capped request sizes; scores come only from the arena's server. Each `/ws` disconnect ends and saves a life, with no rate limit on joins yet: #89 left it out, and it is still open. A per-IP limit has to let `bun run bots`' 200 sockets from one address through.
- The arena needs its WebSocket by design; when the connection drops it shows "Reconnecting..." and rejoins on its own. The life-over screen's reads (best, top 10, totals) show what the server returned and keep the last answer while a poll fails.
- The `/ws` endpoint is public too: names pass `rules.ts` before joining, the `bot ` name prefix is refused from clients, and inputs are validated and rate-limited.
